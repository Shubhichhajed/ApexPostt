# ADR-018: Versioned REST API, API-owned shipment metadata and idempotent scan upload

- **Status:** Accepted
- **Context:** The API must reuse the Week 3 data layer without changing it, expose a stable v1 contract, introduce breaking response changes in v2, and accept the same offline scan more than once.
- **Decision:**
  - URL-segment versioning (`/api/v{version}/...`) with Asp.Versioning. v1 is deprecated with a published sunset date; both versions call the same `IShipmentService`, and only DTOs plus `ShipmentResponseMapper` differ.
  - Recipient contact data, shipment status and uploaded scans are not in the Week 3 `Shipment` model, so they live in additive tables owned by `ApexPostApiDbContext` with its own migration history table. The Week 3 `ApexPostDbContext` is untouched.
  - The scan ID is the primary key of `ShipmentApiScans`; inserts run in a serializable transaction, and a unique-key race is reported as a duplicate. The response returns `accepted`, `duplicatesSkipped` and `rejected` with reasons.
  - The built-in `Microsoft.AspNetCore.OpenApi` generator produces one document per version (OpenAPI 3.0 so NSwag can consume it); Swagger UI only displays them. The C# SDK is generated by NSwag from the committed `contracts/v2.json` at build time.
- **Alternatives:** Header/query versioning (less visible in URLs and docs); editing the Week 3 entity (breaks the "do not change Week 3" constraint); de-duplicating in memory (lost on restart, wrong with several API instances); Swashbuckle generation alongside the built-in generator (two generators, the brief forbids it).
- **Consequences:** Retries from the courier client are safe. Breaking changes are isolated to v2. Contract diffs in `contracts/` make API changes reviewable; regenerating the SDK is just a build.
